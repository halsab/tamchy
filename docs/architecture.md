# Архитектура «Тамчы»

## Реализованные границы

После четвёртого этапа есть React-интерфейс, проверенный каталог, подготовка графики, общий домен игры, браузерные адаптеры и `useGameSession`. Главное меню, три игровых раздела и информация для взрослых подключены к настоящей сессии. Канонические правила: [ТЗ, разделы 4, 9–11](specification.md); ресурсы: [реестр контента](content-guide.md).

Направление зависимостей: контент → домен → React-интеграция → браузерные адаптеры. Домен импортирует существующие `CategoryId` и `LearningItem` только как типы. Он не читает JSON, не проверяет файлы и не повторяет Zod-схему. Вызывающая сторона передаёт раздел из уже проверенного каталога MVP: 4 цвета, 6 животных или 5 чисел. Для иных составов контракт не задан.

| Модуль            | Ответственность                                                                                |
| ----------------- | ---------------------------------------------------------------------------------------------- |
| `models.ts`       | Сессия, раунд, discriminated union состояния, события и идентификаторы операций                |
| `rounds.ts`       | Генератор с переданным источником случайности; собственная последовательность в памяти         |
| `reducer.ts`      | Создание сессии, единственная функция переходов `gameReducer`, вычисляемая подсказка `hasHint` |
| `resources.ts`    | Определение обязательных ресурсов из `LearningItem`, без загрузки                              |
| `requirements.ts` | Чистый селектор `getGameRequirements`: требования текущего состояния к адаптерам               |
| `timing.ts`       | Задержки и сроки из правил игры                                                                |

`tsconfig.game.json` проверяет реализацию без DOM, Node.js и Vite-глобалов. ESLint ограничивает импорты собственными модулями и типами контента, запрещает динамический импорт, `Date`, `globalThis` и `Math.random`. В переходах нет случайности, часов, таймеров и других эффектов. Экраны используют домен только через хук и чистый селектор `hasHint`.

## Сессия и раунды

Для каждого входа нужен новый, не переиспользованный `sessionId`, выбранный внешней стороной. `createRoundGenerator(category, random)` создаётся один раз на сессию. `random()` возвращает число в `[0, 1)`; нарушенный контракт отклоняется. Генератор копирует ID каталога, использует Fisher–Yates и выдаёт каждый ID ровно один раз за цикл. При совпадении первой цели нового цикла с предыдущей целью меняет первые два элемента местами без новых случайных попыток. Помеха выбирается из оставшихся элементов, позиция — отдельным вызовом RNG. На цикл из N элементов требуется N−1 вызовов RNG, на раунд — ещё два. Случайные повторные попытки отсутствуют.

`roundId` — последовательное целое число внутри сессии, начиная с 1. Раунд содержит раздел, цель и readonly-кортеж ровно из двух ID вариантов. Первый раунд передаётся в `createGame(sessionId, category, round, at)`. Последующие принимает только `ROUND_GENERATED` в состоянии перехода: номер должен быть следующим, категория — текущей, варианты — разными и принадлежащими разделу, цель — одним из них и отличаться от предыдущей.

Генератор работает **вне reducer и рендера**. Исполнитель сохраняет один подготовленный следующий раунд по `(sessionId, roundId)` до его принятия. Повторная обработка требования, повторный запуск эффекта и пауза в переходе возвращают тот же подготовленный раунд, а не вызывают генератор снова. После принятия освобождается предыдущий результат; история не нужна. Меняется токен доставки события, но не сам раунд. Иначе можно случайно пропустить номер и цель в цикле. Это реализовано в `features/game/session-rounds.ts`; экземпляр принадлежит сессии и переживает замену исполнителя.

`createGame` копирует элементы и массив вариантов; переходы не мутируют входы. Состояния и контракты readonly. Не сохраняются статистика, счёт или история ответов. Факт правильного ответа представлен текущей фазой и `acceptedAt`; после смены раунда он больше не нужен. Ошибки и использованное напоминание принадлежат одному раунду. Подсказка вычисляется из числа ошибок и отсутствия принятого ответа, включая паузу и ошибку ресурса.

## Состояния и события

Общий контекст содержит сессию, раунд, `operationId`, число ошибок и признак использованного напоминания. Только допустимые для фазы данные находятся в её варианте union.

| Состояние             | Поведение и выход                                                                                                                                                           |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `preparing/resources` | Подготовить обязательные изображения вариантов и полное задание. `RESOURCE_READY` удаляет только соответствующий ожидаемый ресурс; звук запрашивается после готовности всех |
| `preparing/prompt`    | Запросить задание с начала. Только `AUDIO_STARTED` разрешает ответы                                                                                                         |
| `awaiting`            | Задание играет или уже закончилось. `ANSWER` проверяется по ID, не по позиции; дослушивание не требуется                                                                    |
| `retrying`            | Неверный вариант и число ошибок сохранены; звук остановлен. `RETRY_DUE` через 250 мс требует повтор того же задания                                                         |
| `correct`             | Ответ принят один раз; задание отменено. Последовательно подготовить название, запросить звук, получить старт и успешное окончание                                          |
| `transitioning`       | Требуется готовый следующий раунд; повторные ответы и таймеры не действуют                                                                                                  |
| `paused`              | Хранится прерванная фаза. Все операции остановлены; `RETURN` не запускает звук, только явный `CONTINUE` продолжает                                                          |
| `error`               | Хранятся ресурс, причина и фаза восстановления. Ответы заблокированы; `RETRY` явно повторяет подготовку                                                                     |
| `ended`               | Сессия завершена событием `EXIT`; все последующие события игнорируются                                                                                                      |

В нормальном ходе переход после правильного ответа разрешает `ADVANCE_DUE` не раньше `max(acceptedAt + 1200, confirmationEndedAt + 300)`. До успешного окончания подтверждения такого таймера нет. `REPEAT` и ответы в реакции заблокированы. Дубликат окончания не сдвигает срок и не создаёт второй переход.

Неверный ответ увеличивает ошибки один раз и сохраняет цель, порядок и ID раунда. После двух ошибок появляется статичная подсказка до правильного ответа. Автоматического ответа и перехода без ответа нет.

`REPEAT` в ожидании или при запуске задания заменяет запись новой операцией. Во время подготовки ресурсов он явно отменяет и повторяет подготовку. В реакции, ошибке, паузе и переходе это событие игнорируется: для ошибки есть `RETRY`, для паузы — `CONTINUE`.

После `AUDIO_ENDED` задания назначается `IDLE_DUE` на +10 000 мс, если напоминание ещё не использовано. Срабатывание сохраняет `reminderUsed` до конца раунда. Ручные повторы, неправильные ответы, ошибки ресурсов и паузы этот признак не сбрасывают. `ACTIVITY` снимает текущий срок; дубликат окончания не назначает его снова. После нового ручного воспроизведения допустим новый срок, но по-прежнему только одно срабатывание за раунд.

Корень приложения отправляет `ACTIVITY` для любого пользовательского действия, включая нажатие вне игровых кнопок, перед смысловым событием. Недопустимый ID ответа сам по себе оставляет состояние неизменным. Нажатие нормализуется одним обработчиком: нельзя независимо учитывать touch и порождённый им click.

## Идентичность, отмена и время

Каждое событие несёт `(sessionId, roundId, operationId)`. Reducer проверяет весь токен до перехода. Новая загрузка, повтор, принятый ответ, реакция, выход, пауза или восстановление обесценивают прежнюю операцию. Так отсеиваются и старые callbacks внутри того же раунда. Для параллельной подготовки картинок дополнительно сопоставляются вид и точный путь ресурса.

Промежуточная готовность одного файла не меняет токен оставшихся запросов. Фактический старт и окончание одной записи также используют один токен; дубликаты ограничены фазой. Отмена срока бездействия не обесценивает ранее полученную готовность: отсутствие срока в состоянии достаточно для отклонения старого таймера.

Адаптер захватывает токен **при запуске** операции и возвращает его неизменным. Нельзя подставлять текущий токен в старый callback. UI использует токен отображаемого состояния. После выхода и нового входа прежний `sessionId` не используется снова.

Все `at` — конечные неотрицательные миллисекунды единого монотонного источника в пределах сессии. Часы принадлежат внешней стороне. События передаются в порядке наблюдения; срок в требовании не заменяет время фактического callback. Reducer сравнивает срок с переданным временем, ранний таймер игнорирует. Адаптер отвечает за повторное назначение прежнего срока, если его таймер ошибочно сработал раньше. Домен не читает время; исполнитель использует переданный монотонный `GameClock`.

При изменении токена адаптер сначала останавливает прежний звук, отсоединяет обработчики, отменяет запросы и таймеры, затем исполняет новое требование. При неизменном токене выполняет только ещё не начатую работу и снимает исчезнувшие требования. Идентичность JavaScript-объекта не служит основанием для повторного запуска: одинаковый переход reducer можно вычислить несколько раз. Домик и остановка не должны ждать разрешения зависшего Promise.

## Исполнение требований адаптерами

`getGameRequirements(state)` возвращает токен и ровно один вид работы. Это описание текущей потребности, а не очередь команд или универсальный исполнитель эффектов.

| `work.kind`  | Требование                                                                                                               | Обратные события                                                                                                                                     |
| ------------ | ------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prepare`    | Подготовить перечисленные ресурсы до `timeoutAt`; после каждого успеха сверить оставшийся список                         | `RESOURCE_READY` по одному ресурсу; `RESOURCE_FAILED`; `RESOURCE_TIMEOUT` для ещё ожидаемого ресурса                                                 |
| `play`       | Единственная запись с начала. `started: false` — ожидается запуск, `true` — сохранить уже идущую запись с тем же токеном | `AUDIO_STARTED` после фактического старта, затем `AUDIO_ENDED` только после нормального окончания; при ошибке `RESOURCE_FAILED` с указанным ресурсом |
| `wait`       | Звука и загрузки нет. Один срок из `timer`, либо ожидание без таймера                                                    | Указанное `IDLE_DUE`, `RETRY_DUE` или `ADVANCE_DUE` с фактическим временем                                                                           |
| `next-round` | Получить следующий раунд указанного номера вне reducer, сохраняя его при повторной доставке                              | `ROUND_GENERATED` с результатом и токеном запроса                                                                                                    |
| `stop`       | Остановить принадлежащие сессии звук, запросы и таймеры                                                                  | Автоматическое продолжение отсутствует                                                                                                               |

Подготовка изображения означает готовность к показу, аудио — загрузку и декодирование, а не просто успешный HTTP-ответ. В цветах изображения ответов не загружаются: фишки строятся из проверенных данных. У животных обязательны обе картинки. У чисел обе карточки используют один файл яблока, поэтому он подготавливается один раз. Иллюстрации категорий и необязательный декор не входят в подготовку игрового раунда.

Путь `prompt` всегда берётся из `promptAudio`, `confirmation` — из `labelAudio` целевого элемента. Реплики `interaction/` не используются. Разрешение путей относительно Vite `base` остаётся снаружи домена.

У загрузки общий срок +15 000 мс от начала попытки; частичный успех его не продлевает. Ожидание фактического старта записи тоже ограничено 15 000 мс, чтобы зависший запуск можно было явно повторить. Для уже звучащей записи тайм-аут загрузки не применяется. Причины `load`, `decode`, `blocked`, `timeout` — структурированные данные; необработанные технические сообщения в состоянии не хранятся.

Успех, ошибка и отмена различаются. `AUDIO_CANCELLED` не меняет состояние и никогда не заменяется на `AUDIO_ENDED`. При собственной отмене уже действует новая фаза и токен. Если система неожиданно прервала текущую запись, адаптер отправляет `PAUSE`; нельзя оставить игру в ожидании окончания отменённого звука. `DECOR_FAILED` игнорируется.

После ошибки до ответа `RETRY` заново подготавливает ресурсы текущего раунда, используя доступный кэш адаптера. Ошибка подтверждения сохраняет `acceptedAt`; явный повтор готовит и проигрывает только название, затем соблюдает обе границы времени. Повторного зачёта нет.

При `CONTINUE` до ответа заново проверяются ресурсы того же раунда и требуется запуск задания с начала. Ошибка до ответа сохраняет контекст и после возврата требует `RETRY`. После уже принятого правильного ответа продолжение даёт один переход без повторного подтверждения, в том числе при прерванной ошибке подтверждения. Это специальное правило паузы из раздела 10 ТЗ, а не успешное окончание отменённого звука.

## Владение браузерными ресурсами

| Владелец                     | Что создаёт и освобождает                                                                                                                                      |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `useGameSession`             | Один актуальный `GameState` в `useReducer`, экземпляры сервисов, текущий исполнитель, подписки на видимость и прерывания                                       |
| `session-rounds.ts`          | Один генератор с RNG на сессию, один подготовленный раунд до принятия; после выхода ссылка освобождается                                                       |
| `executor.ts`                | Контроллер каждого обязательного ресурса, контроллер воспроизведения, один таймер, токен работы и поколение запуска                                            |
| `assets/images.ts`           | Fetch/декодирование изображения, успешный кэш `HTMLImageElement` и его blob URL; dispose отменяет ожидания, очищает src и отзывает URL                         |
| `audio/audio.ts`             | Единственный ленивый AudioContext, pending-загрузки, активный source и подписка statechange; dispose отсоединяет обработчики и закрывает контекст без ожидания |
| `audio/buffer-cache.ts`      | LRU по пути записи, размер `length × numberOfChannels × 4`; по умолчанию 8 МиБ PCM                                                                             |
| `assets/resource-loading.ts` | Общая небольшая обработка fetch, нормализации ошибок и отмены Promise; pending-запись удаляется после успеха, ошибки и отмены                                  |

Сервисы не создают контекст, изображения или запросы при импорте/рендере. Успешные ресурсы сохраняются между раундами и входами до уничтожения владельца. Изображения загружаются через fetch с проверкой HTTP и полного blob, затем `Image.decode()`; `get(path)` возвращает подготовленное изображение, включая его blob URL. Кэш содержит только запрошенные картинки, включая единственное яблоко. Все сетевые адреса проходят существующий `assetUrl()` с Vite base.

Аудиосервис получает полный `arrayBuffer()`, затем выполняет `decodeAudioData`. Готовность ресурса не равна разрешению воспроизведения. `activate()` вызывается напрямую обработчиком нажатия: создание/resume начинаются синхронно; Promise возвращает результат проверки `context.state`. Подготовка может идти параллельно resume. `play` ждёт эту попытку активации, проверяет состояние снова и создаёт новый source для каждого запуска. `AUDIO_STARTED` отправляется после успешного `source.start()` при работающем контексте; отдельного события started и искусственного таймера нет. Это подтверждение принятого браузерным API запуска, не доказательство слышимости. См. [Web Audio](https://www.w3.org/TR/webaudio/#dom-audiobuffersourcenode-start).

`stop` сначала инвалидирует активную запись, удаляет onended, отменяет ожидание и отсоединяет узел. Только естественное окончание отправляет `AUDIO_ENDED`. Состояние контекста, неожиданно ушедшее из running, останавливает запись и уведомляет хук о паузе. Собственная остановка не вызывает suspend; dispose удаляет statechange до close, поэтому эти действия не создают ложных прерываний. Новый явный `activate` не ждёт старый зависший resume. Отмена сессии никогда не ждёт resume/fetch/decode.

LRU вытесняет давно не использованные неактивные записи. Активный source держит собственную ссылку на AudioBuffer; отдельный буфер больше бюджета не помещается в кэш, но может проигрываться. Размер MP3 не используется для оценки памяти. Вся библиотека не декодируется, предварительная офлайн-подготовка отсутствует.

## Согласование и жизненный цикл

`reconcile(getGameRequirements(state))` сравнивает значения scope и вида работы. Смена scope сначала отменяет прежнюю работу. Частичный `RESOURCE_READY` убирает только соответствующую загрузку; неизменные pending-ресурсы продолжаются. `play.started` не входит в ключ воспроизведения, поэтому старт не останавливает текущий source. Изменённый/удалённый срок снимает старый таймер. `stop` не возобновляет ничего самостоятельно.

Каждый callback захватывает исходный scope, поколение исполнителя и собственный контроллер/таймер. После cancel/dispose или повторного setup старые callbacks не доставляются даже при совпадении доменного токена. Некоторым браузерным операциям недоступна физическая отмена: ожидание прерывается сразу, поздний результат не попадает в кэш или игру, временные blob URL освобождаются. Работа с Promise не удерживает навигацию.

Все сроки вычисляются относительно `performance.now()` либо подменённого `GameClock`. Раннее срабатывание переназначает оставшееся время; события несут фактическое время callback. Кроме самого таймера, исполнитель проверяет дедлайн при готовности ресурса и запуске записи: задержанный браузером callback таймера не позволяет принять запоздалый успех. Промежуточная готовность не продлевает общие 15 секунд. У подготовки и ожидания запуска свои сроки по доменному контракту.

`next-round` готовит результат синхронно вне reducer/рендера и доставляет его микрозадачей с захваченным токеном. Повторное требование не расходует RNG. Отмена доставки, cleanup/setup и пауза сохраняют результат в `SessionRounds`; только принятие соответствующего roundId освобождает его. История не хранится.

## Контракт React-хука

Стабильный `App` вызывает `useGameSession()` и передаёт проверенный раздел в `start(category)` непосредственно из `onClick`. Начало создаёт новый sessionId, активирует звук до любых сетевых ожиданий, создаёт первый раунд и отправляет готовое начальное состояние в useReducer. Обычный вход — явное действие; обработчик адреса и StrictMode не дублируют его. Прямой вход отдельно создаёт раунд с требованием активации, как описано ниже. `gameReducer` остаётся единственным местом продуктовых переходов. Обёртка reducer только устанавливает начало и адресует команды жизненного цикла сессии.

Действия `answer(id)`, `repeat()`, `retry()` и `continueGame()` сначала отправляют ACTIVITY; выход немедленно отменяет работу; отдельное `activity()` предназначено для прочих касаний экрана. Применяется один обработчик click, без независимой обработки touch и порождённого клика. Повтор, повторная попытка и продолжение проверяют разрешение звука непосредственно из обработчика. Рендер читает только состояние; производные признаки, например `hasHint(state)`, вычисляются без дополнительных эффектов.

Выход и скрытие немедленно останавливают исполнитель в стеке обработчика. Команды PAUSE/RETURN/EXIT относятся к сессии, а не к одной её операции: обёртка проверяет sessionId и адресует команду текущему состоянию внутри useReducer. Это сохраняет домик и паузу, если React ещё не применил уже поставленный в очередь ответ. Асинхронные события ресурсов/аудио/таймеров всегда сохраняют исходный OperationScope, без подстановки текущего токена.

`visibilitychange` при скрытии и системное прерывание аудио отправляют PAUSE. Возврат отправляет только RETURN: продолжение и повторная активация требуют действия пользователя. Согласование требований происходит в layout effect до следующей отрисовки, без синхронизации производного состояния. Подписки и работа освобождаются при cleanup. Setup создаёт новые работоспособные сервисы/исполнитель; если сохранена активная сессия, она ставится на паузу с тем же раундом. Это предотвращает повторный старт и использование уничтоженного исполнителя при [цикле React setup → cleanup → setup](https://react.dev/reference/react/useLayoutEffect).

Необязательный объект `GameSessionOptions` задаёт браузерные фабрики, fetch, монотонные часы, RNG, генерацию sessionId и источник видимости. Конфигурация фиксируется при mount; новый объект options на обычном рендере не заменяет сервисы и не прерывает звук. Для намеренной замены границ нужен новый mount. Настоящий cleanup/setup эффектов, например React Activity, всё ещё освобождает ресурсы и ставит сохранённую сессию на паузу. Подмены существуют только в `tests/helpers`; рабочие реализации всегда используют настоящие браузерные API. Для каждого нового входа подменённый генератор sessionId также обязан возвращать новое значение.

Все экраны подключены к одному владельцу. Добавлены все 30 учебных MP3 по путям каталога; отдельный код подключения записей не нужен. Браузерные тесты выполняют настоящие загрузку, декодирование и игровые циклы против `dist`. Ещё 12 файлов из `interaction/` остаются вне сборки и реакций. Слышимость и качество на физических телефонах, Safari/iPhone и офлайн требуют отдельной проверки. [Покрытые сценарии и ограничения](testing.md).

## Экраны и hash-навигация

`app/routes.ts` распознаёт только пять маршрутов и записывает hash с сохранением pathname/base. `App` слушает `hashchange` и `popstate`; программная навигация после `pushState` явно вызывает тот же обработчик согласования. Неизвестный hash заменяется `#/` через `replaceState` без лишней записи истории. Раунды и реакции не обращаются к маршрутам.

`App` находится над переключаемыми экранами и держит один `useGameSession`. Обработчик карточки вызывает стабильный `start(category)` в стеке нажатия, отмечает уже запущенный раздел и меняет маршрут. Обработчик адреса видит эту отметку и не запускает сессию второй раз. При уходе, включая переход к взрослым или в другую категорию, стабильный `exit()` немедленно освобождает исполнителя по текущему `roundsRef`, даже если React ещё не применил старт в том же пакете событий.

Прямой адрес обрабатывается отменяемой микрозадачей после setup, чтобы пробный цикл StrictMode не создавал лишнюю сессию. `start(category, false)` создаёт новый раунд вне рендера и штатную ошибку `blocked` для задания, без создания AudioContext и без автозвука. Крупная кнопка «Тыңла» вызывает `retry()` с активацией в пользовательском жесте. Перезагрузка не восстанавливает данные сессии. Двойное уведомление popstate/hashchange для одного адреса идемпотентно.

После смены экрана фокус переходит на `main`; следующий Tab попадает на первый доступный элемент. Системные жесты, browser back, ориентация и масштабирование не блокируются.

`HomeScreen` отображает три иллюстрированные карточки каталога и вторичную кнопку информации. `GameScreen` отображает доменную фазу, полное задание, два варианта и восстановление; в нём нет игровых таймеров, счётчиков ошибок или проверки правильности ответа. Выделение принятой цели — представление уже вычисленного состояния. `AnswerContent` различает CSS-фишку, иллюстрацию и цифру с фиксированными позициями яблок. Ключ карточки составлен из sessionId, roundId и itemId; повтор, ошибка и перекомпоновка сохраняют её DOM-идентичность.

Все URL разрешаются существующим `assetUrl` с Vite base. Для подготовленной игровой картинки используется blob URL сервиса; до подготовки — URL производного WebP. У каждого изображения зарезервированы размеры. `onError` отображённой картинки отправляет `IMAGE_FAILED` с токеном отображаемого состояния; домен принимает только ресурс текущих вариантов. Он сохраняет контекст ответа/паузы, блокирует ответы, а хук инвалидирует именно этот ресурс в кэше. Явный retry загружает изображение заново. Если ответ уже принят, дополнительная фаза `confirmation/repairing-image` сначала восстанавливает изображение, затем запрашивает название; `acceptedAt` сохраняется. Ошибка декора главного меню не влияет на игровой домен.

`ParentsScreen` получает фактическую версию через подстановку Vite/Vitest из `package.json`. Строки находятся в `tt.json`, новые группы `game` и `parents` проверяются строгой Zod-схемой вместе с прежними ключами. Экран не обещает офлайн, установку или доступное обновление до реализации PWA. Новые тексты пока не прошли языковую приёмку владельцем.
