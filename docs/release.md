# Первый выпуск «Тамчы»

Подготовлен механизм публикации статического PWA версии пакета **0.1.0**. Публикация, настройка GitHub и приёмка на физических устройствах в шестом этапе **не выполнялись**. Зелёная локальная проверка не означает завершение MVP. Требования: [разделы 13–19 ТЗ](specification.md#13-github-pages-и-изоляция), материалы: [реестр](content-guide.md), устройства: [ручной протокол](testing.md#ручной-протокол-iphone-и-android--не-выполнен).

## Настройка перед первым запуском

Владелец выполняет отдельно:

1. Проверить, что основная ветка репозитория — `main`. В **Settings → Pages → Build and deployment → Source** выбрать **GitHub Actions**. Проверить HTTPS. Для репозитория `halsab/tamchy` ожидаемый адрес — `https://halsab.github.io/tamchy/`; фактический адрес берётся из результата `deploy-pages`.
2. Ограничить изменения `main`: pull request с проверкой, обязательное успешное задание `check` workflow «Проверки проекта», запрет force push и удаления ветки. Изменения workflow и зависимостей также проходят рассмотрение. Не обходить проверки при слиянии.
3. Для environment **github-pages** разрешить deployments только из ветки `main`, без сторонних веток и тегов. При доступности required reviewers назначить владельца; перед разрешением первого выпуска проверить таблицу приёмки и материалы. Возможности правил зависят от тарифа и видимости репозитория.
4. Отдельно опубликовать подготовленный коммит в `main` обычным процессом проекта. Проверить успешный push-run. Эта локальная работа не выполняет push и не меняет настройки GitHub.

Workflow сам не включает Pages и не создаёт секреты. Используется штатный `GITHUB_TOKEN`; PAT не нужен. Права по умолчанию — только `contents: read`. Только `deploy` получает `pages: write` и `id-token: write`.

Настройка основана на [официальном руководстве Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages) и [защите environments](https://docs.github.com/en/actions/deployment/targeting-different-environments/managing-environments-for-deployment).

## Ручная публикация

В **Actions → Проверки проекта → Run workflow** выбрать `main`. Ввод произвольного SHA или чужого артефакта не предусмотрен. Каждый ручной запуск заново выполняет все обязательные проверки выбранного коммита для `/tamchy/`, включая настоящий PWA, локальный smoke инструмента публикации и Lighthouse. Публикация зависит от успеха всего задания `check` этого же запуска.

Push и pull request сохраняют обязательные проверки, но не выполняют `deploy`. Ручной запуск из другой ветки также не публикует. Условие публикации дополнительно требует, чтобы default branch оставалась `main`; при переименовании ветки сначала согласованно обновить workflow и правила GitHub.

Все ручные запуски входят в одну concurrency-группу `pages` с `cancel-in-progress: false`. Начатая публикация и её проверка не отменяются новым запуском; push/PR используют другую группу. GitHub может заменить ожидающий запуск более новым: это не очередь всех выпусков. Не запускайте несколько намеренных откатов одновременно.

Environment получает URL из `steps.deployment.outputs.page_url`. После `deploy-pages` обязательно выполняется `check:published`; ошибка оставляет workflow красным, даже если загрузка сайта на Pages уже состоялась. Диагностика сохраняется через `always()`. Автоматического отката нет.

## Какая сборка публикуется

`npm run test:e2e` только для `/tamchy/` выполняет **build → check:assets → check:budgets → полный Playwright** над одной сборкой в `dist`. До браузеров фиксируются хеши всех файлов; после браузеров они должны совпасть. Проверенная копия сохраняется отдельно:

| База       | Проверенные файлы        | Отчёт вне сайта                 |
| ---------- | ------------------------ | ------------------------------- |
| `/tamchy/` | `.release/subpath/dist/` | `.release/subpath/release.json` |

Перед новым `test:e2e` каталог `.release` очищается: старый успех не может заменить неуспешный новый прогон. Фильтрованный запуск, например `--project=chromium`, сохраняет отметку `filtered`; измерения и публикация требуют `full`. Не запускайте одновременно несколько сборок в общий `dist`.

Lighthouse и локальный smoke читают эту копию, проверяя хеши до и после. **После `test:e2e` до измерения и упаковки не запускать build и не редактировать сохранённые файлы.** Workflow упаковывает исключительно `.release/subpath/dist`; база и неизменность артефакта проверяются по отчёту.

`release.json` содержит номер пакета, идентификатор выпуска PWA, полный commit SHA, признак незакоммиченных изменений, базу, вид прогона e2e, бюджеты, размер и SHA-256 каждого файла. Идентификатор выпуска зависит от кода, контента, lockfile и base; он отличается от номера пакета и Git SHA. Локальные результаты до коммита честно имеют `dirty: true` и SHA исходного HEAD. CI требует чистую сборку с `commit === GITHUB_SHA`.

Задание `check` передаёт SHA-256 самого отчёта и ID загруженных артефактов через job outputs. `deploy` скачивает именно эти ID текущего запуска, распаковывает Pages tar, сверяет отчёт с его ожидаемым хешем, а все извлечённые файлы — с отчётом и коммитом. Затем `deploy-pages` публикует исходный неизменяемый `github-pages` того же запуска. Пересборки между проверками и публикацией нет.

Версии B для обновлений создаются в системном временном каталоге и удаляются. Скриншоты, Lighthouse, coverage и отчёты не лежат внутри выбранного `dist`. Проверка состава запрещает мастера, `interaction/`, служебные файлы и любые посторонние ресурсы; сгенерированные manifest/SW вручную не редактируются.

## Артефакты и диагностика

На странице успешного workflow доступны:

| Artifact            | Содержимое                                                                                         |
| ------------------- | -------------------------------------------------------------------------------------------------- |
| `github-pages`      | `artifact.tar` с проверенным `/tamchy/`; только содержимое dist                                    |
| `release-manifest`  | `release.json` с версией, коммитом и всеми хешами                                                  |
| `check-reports`     | Отчёты `/tamchy/`, coverage, e2e, снимки и исходные Lighthouse JSON/HTML; загружается и при ошибке |
| `published-reports` | HTTP-проверка, smoke JSON/trace и диагностика ошибки после публикации                              |

Срок хранения задан в workflow: 30 дней. Сохраните артефакт, отчёт и URL успешного запуска для выбранной рабочей версии до истечения срока. Не определяйте ожидаемую версию чтением живого сайта: берите её из доверенного `release-manifest` успешного запуска.

Локально `npm run release:verify` проверяет выбранную `.release/subpath`. Для скачанного и распакованного комплекта можно передать каталог, содержащий `release.json` и `dist/`: `npm run release:verify -- /path/to/release`. При передаче в CI дополнительно задаются `TAMCHY_REPORT_SHA256` и `GITHUB_SHA`; не подставляйте туда значения из непроверенного отчёта.

## Lighthouse

```sh
npm ci
npx playwright install chromium webkit firefox
npm run test:e2e
npm run check:published:local
npm run check:lighthouse
npm run release:verify
```

Все обычные проверки качества из [testing.md](testing.md#команды-и-ci) также обязательны. `check:lighthouse` ничего не собирает: нужна сохранённая сборка `/tamchy/` после полного `test:e2e`.

Закреплены Lighthouse **13.4.1**, Playwright **1.63.0** и его Chromium; Node **24.20.0**, npm **11.19.0**, CI — `ubuntu-24.04`. Главный экран `/tamchy/` получает ровно три последовательных измерения, каждое в новом временном профиле и новом процессе браузера. Другие тесты во время измерений не запускать. Оригинальный PWA работает, фоновые запросы SW и MP3 дополнительно фиксируются сервером. Кэши перед измерениями не прогреваются.

Одинаковые настройки: mobile Moto G Power, 412×823 CSS px, DPR 1,75, фиксированный мобильный UA; simulated Slow 4G, RTT 150 мс, 1638,4 Кбит/с, CPU slowdown ×4. Также явно зафиксированы параметры DevTools: request latency 562,5 мс, download 1474,56 и upload 675 Кбит/с; выбранный метод — **simulate**, а не фактическое ограничение сети телефона. Локальный сервер отдаёт текстовые ресурсы gzip, без SPA-подмены отсутствующих файлов. Настоящий Pages проверяется отдельно.

Для каждого вызова создаются новые `reports/lighthouse-subpath-*/`: три исходных JSON/HTML, окружение и запросы каждого прогона, `summary.json`. В них сохранены фактические версии Lighthouse/Chromium, ОС, CPU, Node, effective settings, связь с отчётом артефакта и каждый результат. Неудачные прогоны и предыдущие серии не удаляются и не заменяются дополнительными попытками ради медианы.

Проходной критерий — независимые медианы **LCP ≤2500 мс**, **CLS ≤0,1**. Неполные или некорректные измерения означают ошибку. Общий performance score не используется как критерий. Lighthouse не подтверждает p95 реакции на касание ≤100 мс и качество звука на физическом устройстве. Методика опирается на [конфигурацию Lighthouse](https://github.com/GoogleChrome/lighthouse/blob/v13.4.1/docs/configuration.md) и [описание throttling](https://github.com/GoogleChrome/lighthouse/blob/v13.4.1/docs/throttling.md).

## Проверка фактического адреса

После публикации workflow использует URL из `deploy-pages`. Для независимой ручной проверки скачайте `release-manifest` того же успешного запуска и выполните в соответствующей версии репозитория:

```sh
npm ci
npx playwright install chromium
npm run check:published -- https://halsab.github.io/tamchy/ EXPECTED_RELEASE /path/to/release.json
```

Замените `EXPECTED_RELEASE` идентификатором из проверенного отчёта. URL должен содержать завершающий `/`, без hash и query. Команда читает главный URL, index.html и все файлы отчёта, включая манифест, SW, его зависимости и весь обязательный контент. Проверяются HTTP 200, тип содержимого, длина и SHA-256, base/id/scope/start_url и идентификатор выпуска. Перенаправления, HTML вместо MP3/WebP/JS, пропавший или изменённый файл завершают проверку ошибкой.

Затем свежий Chromium открывает главное меню, входит во все три раздела, ждёт разрешённых ответов после настоящего старта задания, получает и декодирует реальный MP3 каждого раздела, возвращается домой. Проверяются видимый идентификатор выпуска у взрослых, активный SW, ошибки консоли/HTTP и запросы за пределы приложения. Это небольшой smoke, а не повтор всей приёмки и не проверка слышимости динамика.

Диагностика — `reports/published/`, либо каталог `TAMCHY_PUBLISHED_REPORTS`. `npm run check:published:local` проверяет тот же инструмент на локальном HTTP-сервере для сохранённой `/tamchy/`. Контролируемые HTTP-ошибки покрыты модульными тестами. **Локальный HTTP не является подтверждением GitHub Pages.**

## Откат

1. Зафиксировать неуспешный URL, release, SHA и workflow run; изучить `published-reports`. Успешный deploy с неуспешным smoke уже мог изменить сервер.
2. Найти последнюю проверенную рабочую версию по сохранённым артефактам и отчётам. Подготовить обычный PR в `main`, отменяющий проблемные изменения кода/контента через `git revert` или восстанавливающий нужные файлы из этой версии. Сохранить действующие проверки и безопасный workflow; не делать force push и не переписывать историю.
3. После рассмотрения PR и успешных проверок запустить ручной workflow из `main`. Получится новый проверенный коммит, воспроизводящий рабочее содержимое, со своим отчётом. Не подсовывать старый tar без повторного проверенного процесса и не запускать публикацию из старой сторонней ветки.
4. Проверить фактический URL с ожидаемым release нового запуска. Повторить протокол обновления: открытая старая игра продолжает работать, возвращённая версия активируется естественно после закрытия всех старых вкладок/окон. Проверить запуск и полный офлайн на устройствах.

Откат сервера не обновляет мгновенно открытое или отключённое от сети приложение. Не вызывать `skipWaiting`, не перезагружать игру, не очищать все кэши домена и не снимать чужие регистрации.
